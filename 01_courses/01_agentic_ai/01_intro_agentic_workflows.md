## 1. 코스 및 Agentic AI 소개

### 1.1 Agentic AI 용어와 hype

- ==**“agentic”**== 이라는 용어를 만든 이유: 사람들이 LLM 기반 애플리케이션을 만드는 방식에서 **중요하고 빠르게 성장하는 트렌드**를 보고 이를 표현할 단어가 필요했기 때문.
        
- 예상치 못한 일: 마케터들이 이 단어를 **스티커처럼 온갖 것에 붙이기 시작**했고, 그 결과 Agentic AI 관련 **하이프(과열된 관심)**가 폭발적으로 증가.
        
- 긍정적인 측면:
    
    - 과장된 열기를 제외하고 보더라도, **진짜로 유용하고 가치 있는 Agentic AI 애플리케이션 수도 매우 빠르게 증가**했다.
        
    - hype만큼은 아니어도 실제 좋은 사용 사례가 꾸준히 늘고 있음.
        
- 이 코스의 목표:
    
    - **Agentic AI 애플리케이션을 잘 만드는 best practice**를 알려 주는 것.
        
    - 이를 통해 “내가 무엇을 만들 수 있는가”의 범위를 크게 넓혀주는 것.
        

### 1.2 오늘날 Agentic 워크플로가 쓰이는 대표적인 예시

- **고객지원 에이전트**:
    
    - 고객 문의에 자동으로 응답하는 시스템.
        
- **딥 리서치 에이전트**:
    
    - 복잡한 주제를 깊게 조사하고,
        
    - **깊이 있는 리서치 리포트**를 작성.
        
- **복잡한 법률 문서 처리**:
    
    - tricky한 계약서나 법률 문서를 이해하고 요약/분석.
        
- **의료 입력 분석 및 진단 제안**:
    
    - 환자 입력(증상 설명 등)을 보고,
        
    - 가능한 의료적 진단을 제안(의사 보조용).
        
- 강의자의 팀 경험:
    
    - 여러 팀에서 수행한 많은 프로젝트들이 **agentic 워크플로 없이는 사실상 불가능**했음.
        
    - 따라서 이러한 워크플로를 설계/구현하는 능력은 **오늘날 AI에서 가장 중요한 스킬 중 하나**.

### 1.3 잘하는 사람 vs 덜 잘하는 사람의 차이: Eval & Error Analysis

- Agentic 워크플로를 정말 잘 만드는 사람과 그렇지 않은 사람의 차이 중 하나:
    
    - **디시플린 있는(deisciplined) 개발 프로세스**를 갖추었는가.
        
    - 특히 ==**evals(평가)와 error analysis(오류 분석)에 초점을 둔 개발 프로세스**==를 가지고 있는가.
        
- 이 코스에서 다루는 것: Eval과 error analysis가 무엇인지, 그것이 어떻게 **에이전틱 워크플로를 잘 만들고 개선하는 핵심 요소**가 되는지.
        
- 결과적으로: 이런 능력은 **일자리 기회**, 그리고 **내가 직접 뛰어난 소프트웨어를 만드는 기회**를 크게 늘려줌.

## 2. Agentic AI란 무엇인가? 왜 강력한가?

### 2.1 전통적인 LLM 사용 방식(비-agentic)

- 오늘날 많은 사람들이 LLM을 사용하는 방식: “주제 X에 대한 에세이를 써 줘” 같은 식으로 **한 번에 전체 결과를 생성**하도록 요청.

- 비유:
    인간(또는 AI)에게 “처음 단어부터 마지막 단어까지 **한 번에 쭉** 써라” “중간에 **backspace도 쓰지 말고** 수정 없이 타이핑하라” 라고 요구하는 것과 비슷.

- 현실: 사람도 이렇게 쓰면 **좋은 글을 쓰기 어렵고**,AI 모델도 마찬가지.
	그럼에도 불구하고:LLM은 이런 **제약된, 완전 선형적인 방식**에서도 놀라울 정도로 꽤 잘 수행.


### 2.2 Agentic 워크플로의 예: 에세이 작성

- Agentic 접근에서는 프로세스가 다음처럼 변함:

    1. 특정 주제에 대한 **에세이 아웃라인** 먼저 작성.
        
    2. 이후 **웹 리서치가 필요한지** 결정.
        
    3. 웹 리서치를 수행하고 웹 페이지를 다운로드.
        
    4. 그 정보를 바탕으로 **첫 번째 초안(first draft)** 작성.
        
    5. 초안을 다시 읽고, 어떤 부분이 **수정/추가 리서치가 필요한지** 판단.
        
    6. 필요 시 추가 리서치 및 **수정(revise)** 반복.

- 이 프로세스는: 생각 → 조사 → 작성 → 다시 생각 → 수정 → 또 조사 …
        
    - 인간이 실제로 글을 쓸 때 하는 **반복적·비선형 과정**과 유사.

- 결과: Agentic 워크플로는 종종 **더 오래 걸리지만**, **훨씬 더 좋은 결과물**을 만들어 낸다.


### 2.3 Agentic AI 워크플로 정의

- **정의**: Agentic AI 워크플로는 **LLM 기반 앱이 하나의 태스크를 완료하기 위해 여러 단계를 순차/반복적으로 실행하는 과정**.
        
- 에세이 예시에서 각 단계:
    
    - LLM을 사용해 **에세이 아웃라인** 생성.
        
    - LLM을 사용해 웹 검색에 쓸 **검색어를 생성**.
        
    - 웹 검색 API를 호출해 **관련 웹페이지를 다운로드**.
        
    - 다운로드한 웹 페이지 내용을 LLM에 입력해 **첫 draft 작성**.
        
    - 또 다른 LLM 또는 같은 LLM을 사용해 **초안을 리뷰하고 무엇을 고칠지 결정**.
        
    - 필요 시 **인간 리뷰(human-in-the-loop)** 단계를 추가:
        
        - 예: 중요한 사실(fact)을 인간 검토자에게 확인 요청.
            
    - 리뷰 결과를 반영하여 **다시 수정**.
        
- 핵심 스킬:
    
    - 복잡한 태스크(예: 에세이 작성)를 ==**쪼개서 여러 단계==로 나누는 능력**.
        
    - 각 단계를 잘 수행할 수 있도록 ==**컴포넌트를 설계/구현==하는 능력**.
        
    - 이 능력이 있어야 다양한 **흥미로운 Agentic 애플리케이션**을 만들 수 있음.

## 3. Running Example: Research Agent

### 3.1 예시: SpaceX와 경쟁할 로켓 회사 리서치

- 코스 전체에서 함께 만들 **러닝 예제**: **Research Agent (연구 에이전트)**.
    
- 예시 프롬프트: “SpaceX와 경쟁할 새로운 로켓 회사를 어떻게 만들 수 있는지” 같은 리서치 토픽을 입력.
- 
- 에이전트 동작:
    
    1. **어떤 리서치를 할지 계획** 수립.
        
    2. 웹 검색 엔진을 호출하여 **웹 페이지 다운로드**.
        
    3. 웹 페이지들을 분석하여 **finding을 정리·랭킹**.
        
    4. **아웃라인 초안(draft outline)** 작성.
        
    5. “editor” 역할의 에이전트가 **coherence(일관성)**를 검토.
        
    6. 최종적으로 **포괄적인 마크다운 리포트** 생성.        
        - 예: 제목, intro, background, findings 등.

- 코멘트:
    
    - SpaceX와 경쟁하는 스타트업은 **매우 어려운 사업**임을 리포트가 적절히 지적.
        
    - 강의자는 실제로 할 생각은 없지만, 이런 종류의 아이디어를 **초기 리서치**하는 데 research agent가 매우 유용할 수 있다고 설명.
        
- 장점:
    
    - 여러 소스를 찾아서 다운로드하고,
        
    - ==깊게 생각(분석·조합)==한 뒤 리포트를 쓰기 때문에,
        
    - 그냥 “에세이 써 줘” 한 번 프롬팅하는 것보다 **훨씬 깊이 있는 결과**를 제공.
        

### 3.2 실전 활용 경험

- 강의자는 이미 여러 분야에서 **전문화된 연구 에이전트**를 실무에 활용:
    
    - 법률 문서, 컴플라이언스 관련 리서치.
        
    - 헬스케어 도메인의 특정 섹터.
        
    - 비즈니스/제품 리서치 영역 등.

- 이 코스를 통해: 다양한 분야에 쓸 수 있는 agentic 워크플로를 배우는 동시에, **custom research agent를 직접 만드는 데 바로 활용 가능한 아이디어**도 얻는 것이 목표.

## 4. 에이전트의 자율성(Autonomy) 스펙트럼

### 4.1 Agent vs Agentic 용어 논쟁

- 과거 AI 커뮤니티에서 논쟁:
    
    - “이건 에이전트다”, “이건 진짜 에이전트가 아니다” 같은 논의가 많았음.
        
    - 어떤 논문은 “우리는 agent를 만들었다”고 주장하고,
        
    - 다른 사람들은 “그건 진짜 에이전트가 아니다”라고 반박.

- 강의자의 관점:
    
    - 이 논쟁이 **불필요**하다고 느낌.
        
    - 그래서 **“agentic”** 이라는 형용사(adjective)를 쓰기 시작.

    - 이유:
        
        - “에이전트냐 아니냐”라는 **이분법(binary)** 대신,
            
        - 시스템이 **얼마나 agentic한가(얼마나 자율적인가)**라는 **연속적인 스펙트럼**으로 보자는 것.
            
    - 이렇게 하면 “진짜 에이전트냐 아니냐”를 싸우지 말고,
        
        - “얼마나 agentic한 시스템인가?”를 인정하고
            
        - **실제 시스템을 만드는 일에 집중**할 수 있음.
            
- 강의자의 팀 일화:
    
    - “우리에겐 agent라는 단어도 있는데 왜 또 새로운 단어가 필요하냐”라는 피드백도 있었지만,
        
    - 결국 agentic을 사용했고,
        
    - 나중에 뉴스레터(The Batch)와 SNS에서
        
        - “어떤 것이 진짜 에이전트냐 싸우지 말고,  
            시스템들이 서로 다른 정도의 agentic 성을 가진다고 인정하자”
            
        - 라고 제안함.
            
    - 이 관점이 논쟁을 진정시키고 **구현에 집중하는 분위기**를 만드는데 도움.
        

### 4.2 덜 자율적인 에이전트 예시

- 예: **“블랙홀에 대한 에세이”** 작성 에이전트
    
    - 간단한 agentic 설계:
        
        1. LLM이 몇 개의 **웹 검색어**를 생성.
            
        2. 하드코딩된 로직으로 **웹 검색 엔진 호출**.
            
        3. 결과 웹페이지들을 **fetch**.
            
        4. LLM이 이들을 바탕으로 에세이 작성.
            
- 특징:
    
    - **완전히 결정적인(deterministic) 순서**의 단계.
        
    - 어떤 단계에서 무엇을 할지 **프로그래머가 미리 다 정해둠**.
        
    - 이 경우도 충분히 잘 작동할 수 있지만,
        
    - 자율성 수준은 상대적으로 낮음.
        
- 표기 규칙 (이 강의 전체에서 사용하는 다이어그램 표기법):
    
    - **빨간색(red)**: 사용자 입력 (예: 사용자 쿼리, 입력 문서).
        
    - **회색(gray) 상자**: LLM 호출.
        
    - **녹색(green) 상자**: 다른 소프트웨어/툴 호출
        
        - 예: 웹 검색 API, 웹 페이지 fetch 코드 실행 등.
            

### 4.3 더 자율적인 에이전트 예시

- 더 자율적인 버전의 블랙홀 에세이 에이전트:
    
    - 주어진 입력: “블랙홀에 대한 에세이를 써라”
        
    - LLM이 결정할 수 있는 것:
        
        - 웹 검색을 할지 여부.
            
        - 최신 뉴스 소스를 검색할지,  
            arXiv 같은 연구 논문 사이트를 검색할지.
            
        - 어느 검색 엔진/데이터 소스를 사용할지.
            
        - PDF를 가져왔다면, PDF → 텍스트 변환 도구를 호출할지 여부.
            
        - 몇 개의 웹 페이지를 가져올지.
            
        - 중간에 다시 리플렉션을 할지, 더 웹 페이지를 가져올지 등.
            
- 특징:
    
    - LLM이 **결정권을 많이 가진다**:
        
        - 어떤 도구를 언제 호출할지.
            
        - 어떤 순서로 단계들을 실행할지.
            
    - 결과적으로 **실행되는 실제 단계 순서가 매번 달라질 수도 있고**,  
        이는 프로그래머가 아닌 **LLM에 의해 결정**됨.
        

### 4.4 자율성 스펙트럼 정리

- **덜 자율적인 시스템**:
    
    - 모든 단계가 미리 정해져 있고,
        
    - 어떤 함수/툴을 호출할지도 **하드코딩**.
        
    - LLM의 자율성은 주로 **텍스트 출력 내용**에 국한.
        
- **매우 자율적인 에이전트**:
    
    - 어떤 순서로 어떤 단계를 수행할지 **스스로 결정**.
        
    - 심지어 **새로운 함수/툴을 만들어 실행**하기도 함.
        
- **중간 단계(세미-autonomous)**:
    
    - 일부 의사결정은 LLM이 하지만,
        
    - 사용할 수 있는 도구나 구조는 어느 정도 **미리 정의(predefined)**.
        
- 이 코스에서:
    
    - 이 스펙트럼 전반에 걸친 다양한 예제를 다룸.
        
    - 실제 비즈니스에서는
        
        - **덜 자율적인 쪽**에도 이미 엄청나게 많은 유용한 애플리케이션이 존재.
            
        - **더 자율적인 쪽**은
            
            - 더 **통제하기 어렵고, 예측 불가능한 면**이 있고,
                
            - 동시에 현재 매우 활발한 **연구 분야**.

## 5. 왜 Agentic 워크플로를 쓰는가? (장점)

### 5.1 가장 큰 장점: 기존에 불가능하던 일을 가능하게 함

- 가장 큰 이점:
    
    - Agentic 워크플로는 **예전에는 사실상 불가능했던 많은 작업을 가능하게** 한다.
        
- 그 외 장점:
    
    - **병렬성(parallelism)**:
        
        - 여러 작업을 동시에 실행해 속도를 높일 수 있음.
            
    - **모듈성(modularity)**:
        
        - 다양한 컴포넌트를 조합해 **최적의 워크플로**를 만들 수 있음.
            

### 5.2 HumanEval 코드 벤치마크 예시

- 팀에서 수집한 데이터:
    
    - 코드 작성 능력을 평가하는 벤치마크인 **HumanEval**에서,
        
    - 서로 다른 LLM의 성능을 비교.
        
- 결과:
    
    - **GPT-3.5** (초기 ChatGPT 기반 모델)
        
        - “코드를 직접 한 번에 쓰게 하는” non-agentic 방식:
            
        - 약 **40%** 정답률.
            
    - **GPT-4** (더 강력한 차세대 모델)
        
        - 동일하게 non-agentic 직접 코드 생성:
            
        - 약 **67%** 정답률.
            
- 세대 차이 효과 vs. Agentic 효과:
    
    - GPT-3.5 → GPT-4로의 변화는 **모델 세대에 따른 엄청난 향상**.
        
    - 그런데 **GPT-3.5에 Agentic 워크플로를 씌우면**:
        
        - 예: 코드 작성 → 코드에 대해 스스로 반성/수정(Reflection) → 다시 시도 등.
            
        - GPT-3.5만으로도 **훨씬 더 높은 성능**을 낼 수 있음.
            
    - 마찬가지로 GPT-4도 Agentic 워크플로와 함께 쓰면 성능이 더 올라감.
        
- 요점:
    
    - **모델 세대 업그레이드**도 중요하지만,
        
    - 때로는 **이전 세대 모델 + Agentic 워크플로**가  
        “새로운 세대 모델을 그냥 쓰는 것”보다 **더 큰 효과**를 내기도 한다.
        

### 5.3 병렬화에 의한 속도 이점

- 예: “블랙홀에 대한 에세이 써줘”
    
    - Agentic 워크플로에서 할 수 있는 최적화:
        
        - 3개의 LLM을 **병렬로** 돌려 각각 다른 **검색어를 생성**.
            
        - 각 검색어로 웹 검색을 수행하고,
            
        - 각 검색 결과에서 **여러 웹 페이지를 동시에 다운로드**.
            
    - 사람이라면:
        
        - 9개의 웹 페이지를 **하나씩 순차적으로** 읽어야 함.
            
    - Agentic 워크플로:
        
        - 9개 웹 페이지를 **동시에 fetch**해 놓고,
            
        - 이후 LLM이 한 번에 이를 입력으로 받아 에세이 작성.
            
- 비교:
    
    - Non-agentic: LLM 한 번 호출 → 빠르지만 얕음.
        
    - Agentic:
        
        - Non-agentic보다는 시간이 더 걸릴 수 있으나,
            
        - 사람이 직접 리서치하는 것과 비교하면
            
            - **병렬 다운로드 덕분에 훨씬 빠르게** 많은 정보를 처리 가능.
                

### 5.4 모듈성: 웹 검색 엔진·LLM 교체

- Agentic 워크플로 설계 시 자주 하는 작업:
    
    - 각 **컴포넌트(LLM, 웹 검색 엔진, 뉴스 검색, 코드 실행 등)**를 별도의 모듈로 보고,
        
    - 필요에 따라 **교체(swap)** 또는 **추가**.
        
- 예:
    
    - 웹 검색 엔진:
        
        - Google, Bing, DuckDuckGo, Tavily, u.com 등 다양한 선택지.
            
        - 필요에 따라 **기존 엔진을 다른 엔진으로 교체** 가능.
            
    - 뉴스 검색 엔진:
        
        - 특정 단계에서 일반 웹 검색 대신 **뉴스 검색 엔진을 사용**해 최신 연구/뉴스 반영.
            
    - LLM 교체:
        
        - 모든 단계에 동일 LLM을 쓰지 않고,
            
        - 각 단계마다 **다른 LLM** 또는 **다른 제공자**를 써서 결과 비교.
            
- 요약:
    
    - Agentic 워크플로의 모듈 구조 덕분에
        
        - 성능 개선을 위해 **툴과 모델을 유연하게 교체/추가**할 수 있음.

## 6. Agentic AI 애플리케이션 사례

### 6.1 예시 1: 인보이스 처리(Invoice Processing)

- 태스크:
    
    - 인보이스(PDF)를 받아서,
        
    - **핵심 필드**를 추출해 데이터베이스에 저장.
        
    - 예:
        
        - biller: Tech Flow Solutions
            
        - biller address
            
        - amount due: $3,000
            
        - due date: 2025년 8월 20일
            
- Agentic 워크플로:
    
    1. **입력**: 인보이스(PDF).
        
    2. PDF → 텍스트 변환 API 호출:
        
        - LLM이 읽기 쉬운 형식(예: Markdown 텍스트)으로 변환.
            
    3. LLM:
        
        - 문서를 보고 **이게 실제 인보이스인지** 아니면 다른 문서인지 판단.
            
        - 인보이스라면 필요한 필드 추출.
            
    4. 도구/API:
        
        - 추출한 필드를 사용해 **데이터베이스 레코드 업데이트**.
            
- 특징:
    
    - “필수 필드를 추출하고 DB에 기록한다”라는 **명확한 절차**가 있음.
        
    - 이렇게 **clear한 step-by-step 프로세스**가 있으면  
        Agentic 워크플로 구현이 비교적 쉽고 안정적.
        

### 6.2 예시 2: 기본적인 고객 주문 문의 응답 에이전트

- 태스크:
    
    - 고객이 보낸 이메일에 대해,
        
    - 주문 정보 확인 후 **응답 초안 작성**,  
        그리고 필요 시 인간이 리뷰 후 발송.
        
- 단계:
    
    1. **키 정보 추출**:
        
        - 고객이 누군지
            
        - 무엇을 주문했는지
            
        - 주문 번호
            
    2. **주문 데이터 조회**:
        
        - 주문 DB를 조회하는 함수/툴을 호출하여 주문 정보 가져오기.
            
    3. **응답 초안 작성**:
        
        - LLM이 이메일 답변 초안 작성.
            
    4. **인간 리뷰 큐에 넣기**:
        
        - LLM이 “request review” 툴을 사용해,
            
        - 초안을 **인간이 검토하는 큐에 등록**.
            
        - 사람이 확인 후 고객에게 발송.
            
- 워크플로 다이어그램(개념):
    
    - 이메일 → LLM (정보 추출) → 주문 DB 툴 호출 → 결과 → LLM (답변 작성)  
        → review 툴(큐에 넣기) → 인간 검토 → 발송.
        
- 현실:
    
    - 이런 고객 주문 문의 에이전트는 이미 **많은 기업에서 실제 운영 중**.
        

### 6.3 예시 3: 더 일반적인 고객 서비스 에이전트

- 더 어려운 예:
    
    - 주문 문의뿐 아니라, **더 일반적이고 다양한 질문**에 응답.
        
- 예1: “검은색/파란색 청바지 있나요?”
    
    - 필요한 단계:
        
        1. 해당 질문의 의미를 분석.
            
        2. “black jeans”, “blue jeans” 각각에 대해 **재고 조회 API를 여러 번 호출**.
            
        3. 결과를 조합해 고객에게 답변.
            
- 예2: “전에 샀던 비치 타월을 반환하고 싶어요.”
    
    - 필요한 단계:
        
        1. 고객이 실제로 **비치 타월을 구매했는지 검증**.
            
        2. **반품 정책 확인**:
            
            - 예: 구매 후 30일 이내, 사용하지 않은 상태여야 함 등.
                
        3. 조건을 만족하면:
            
            - 반품 팩킹 슬립 발급.
                
            - DB에서 해당 주문 상태를 “return pending”으로 설정.
                
- 특징:
    
    - 이 경우, 요청을 처리하기 위한 **필요 단계가 사전에 확정되어 있지 않을 수 있음**.
        
    - 따라서:
        
        - LLM 기반 애플리케이션이
            
            - 어떤 단계가 필요한지 **스스로 계획/추론**해야 함.
                
        - 이 때문에 훨씬 더 **어렵고 예측 불가능한 워크플로**가 됨.
            
    - 이 강의에서는 이런 문제를 다루는 **최신 기법들**도 함께 소개.
        

### 6.4 예시 4: 컴퓨터 사용(Computer Use) 에이전트

- cutting-edge 예시:
    
    - 에이전트가 웹 브라우저를 직접 사용하여
        
    - 웹 페이지를 읽고 조작해 **복잡한 태스크를 수행**.
        
- 데모 시나리오:
    
    - “샌프란시스코 → 워싱턴 DC(DCA)로 가는 두 개의 유나이티드 항공편에 좌석이 있는지 확인해 줘.”
        
- 에이전트의 행동:
    
    1. 웹 브라우저 접근 권한이 있음.
        
    2. United Airlines 웹사이트에 접속.
        
    3. 폼 필드를 채우고 버튼을 클릭하는 등,
        
        - 사람처럼 웹 페이지를 탐색하고 조작.
            
    4. 페이지 내용을 읽고 “다음에 무엇을 해야 할지” 추론.
        
    5. 사이트에서 문제가 생기자 Google Flights로 이동.
        
    6. 거기서 요청에 맞는 항공편 여러 개를 찾음.
        
    7. 하나를 선택하면 다시 United 사이트로 돌아옴.
        
    8. 최종적으로 “요청한 항공편에 좌석이 있다”고 판단.
        
- 현재 상태:
    
    - 매우 흥미롭고 중요한 **연구 영역**.
        
    - 하지만:
        
        - 페이지 로딩이 느리면 상황을 잘 이해하지 못하거나,
            
        - 복잡한 웹 페이지는 아직 정확히 파악하지 못하는 경우가 많음.
            
    - 그래서 아직은 **mission-critical 용도로 쓰기엔 신뢰성이 부족**하지만,
        
    - 앞으로 발전 가능성이 매우 큰 분야.
        

### 6.5 어떤 태스크가 쉬운지 vs 어려운지

- **더 쉬운 태스크**:
    
    - **명확한 단계별 절차**가 있는 업무.
        
    - 비즈니스가 이미 **표준 운영 절차(SOP)**를 가지고 있는 경우.
        
    - 이런 절차를 Agentic 워크플로로 **코딩하는 작업은 수고가 크지만, 구조가 안정적**이라 구현이 비교적 쉽다.
        
    - 특히 **텍스트만 다루는 경우**:
        
        - LLM은 원래 텍스트 처리에 최적화되어 있어 수행이 더 안정적.
            
- **더 어려운 태스크**:
    
    - 필요한 단계들이 **사전에 알려져 있지 않은 경우**:
        
        - 앞서 본 고급 고객 서비스 에이전트처럼,
            
        - 에이전트가 **실시간으로 계획을 세워야 하는 태스크**.
            
    - **멀티모달 입력**(이미지, 오디오, 비디오 등)을 많이 처리해야 하는 경우:
        
        - 텍스트-only보다 흔히 **덜 안정적**임.
            
- 정리:
    
    - Agentic 워크플로를 설계할 때,
        
        - “이 업무가 얼마나 명확한 절차를 갖고 있는지”
            
        - “텍스트-only인지, 멀티모달인지”
            
        - 를 기준으로 구현 난이도를 가늠할 수 있다.

## 7. Task Decomposition (작업 분해)

### 7.1 연구 에이전트 예시에서의 분해

- 문제:
    
    - “주제 X에 대해 에세이를 써라”를 그냥 LLM에 직접 요청하면,
        
    - 결과가 **표면적인 내용**만 다루거나 **당연한 사실만 나열**하는 경우 많음.
        
- 해결 방향:
    
    - “사람이라면 이 에세이를 어떻게 쓸까?”를 생각해 봄.
        
        - 바로 쓰기보다는
            
            1. 아웃라인 작성
                
            2. 웹 리서치
                
            3. 리서치 결과를 바탕으로 에세이 작성
                
        - 등 여러 단계를 거칠 것.
            
- 작업 분해의 핵심 질문:
    
    - 각 단계(예: 1, 2, 3)에 대해
        
        - “이 단계는 LLM, 짧은 코드, 함수 호출, 툴 중 하나로 구현 가능할까?”
            
- 예:
    
    - 1단계: 아웃라인 작성 → LLM이 충분히 잘 할 수 있음.
        
    - 2단계: 웹 검색에 쓸 검색어 생성 → LLM으로 구현 가능.
        
    - 3단계: 검색 결과를 바탕으로 에세이 작성 → LLM으로 구현 가능.
        
- 이렇게 해서 기본적인 **3단계 Agentic 워크플로**를 구성.
    

### 7.2 분해 후 다시 분해: 품질 개선

- 초기 워크플로를 구현해 결과를 확인해 보니:
    
    - 에세이가 여전히 충분히 **깊지도 않고, 일관성도 떨어지는** 느낌.
        
    - 시작, 중간, 끝 사이의 **연결이 매끄럽지 않다(disjointed)**고 느낌.
        
- 대응:
    
    - 문제가 되는 단계(예: “3. 에세이 작성”)를 **다시 분해**.
        
- 새 워크플로:
    
    - 3단계를 다음처럼 세부 단계로 쪼갬:
        
        1. 첫 draft 작성.
            
        2. 어떤 부분이 수정/추가가 필요한지 평가.
            
        3. draft를 수정(revise).
            
    - 이것은 사람이 글 쓸 때
        
        - 처음부터 완성본을 쓰지 않고,
            
        - 초안을 쓰고, 읽고, 비판하고, 수정하는 과정과 같음.
            
- 결과:
    
    - 전체 프로세스가
        
        - “직접 한 번에 에세이 생성” → “3단계” → 다시 “더 세부적인 여러 단계”로 발전.
            
    - 필요하다면 이 과정을 계속 반복해서 프로세스를 더 세밀하게 조정.
        

### 7.3 고객 주문 문의 예시에서의 분해

- 태스크: 기본 고객 주문 문의 대응
    
- 분해:
    
    1. **핵심 정보 추출**:
        
        - 이메일에서 발신자, 주문 품목, 주문 번호 등.
            
        - LLM이 담당 가능.
            
    2. **고객 레코드 조회**:
        
        - 주문 DB에 쿼리를 날리는 함수/툴을 LLM이 호출.
            
    3. **답변 작성 및 이메일 발송**:
        
        - LLM이 이메일 내용을 작성.
            
        - 이메일 발송 API를 호출해 실제로 전송.
            
- 각 단계에 대해:
    
    - “LLM + 함수/툴 호출”로 구현 가능하다고 판단되면,
        
    - 그 단계를 Agentic 워크플로에 포함.
        

### 7.4 인보이스 처리 예시에서의 분해

- 태스크: 인보이스 처리
    
- 분해:
    
    1. PDF → 텍스트 변환(이미 전 단계에서 수행).
        
    2. LLM이 **필수 필드 추출**:
        
        - biller 이름, 주소, amount due, due date 등.
            
    3. LLM + 함수 호출로 **DB 레코드 업데이트**.
        
- 구현:
    
    - Agentic 워크플로는 이 두 단계(추출, DB 업데이트)를 차례로 수행하도록 구성.
        

### 7.5 빌딩 블록 관점

- Agentic 워크플로를 만들 때 사용하는 주요 빌딩 블록:
    
    1. **LLM / LMM (Large Language/Multimodal Model)**:
        
        - 텍스트 생성, 결정, 정보 추출 등에 사용.
            
    2. **기타 AI 모델**:
        
        - PDF → 텍스트 변환 모델.
            
        - TTS(text-to-speech).
            
        - 이미지 분석 모델 등.
            
    3. **소프트웨어 도구(툴)**:
        
        - 웹 검색 API.
            
        - 실시간 날씨 API.
            
        - 이메일/캘린더 연동.
            
    4. **정보 조회 도구**:
        
        - 데이터베이스 조회/업데이트.
            
        - RAG(정보 검색 및 관련 텍스트 반환) 시스템.
            
    5. **코드 실행 도구**:
        
        - LLM이 작성한 코드를 실제로 실행하는 환경.
            
- 많은 Agentic 워크플로 설계 작업은:
    
    - “사람이/비즈니스가 하는 일을 관찰하고,
        
    - 이 빌딩 블록들을 어떤 순서로 조합해야  
        그 일을 잘 수행할 수 있을지 설계하는 일”.
        
- 따라서:
    
    - 어떤 빌딩 블록을 사용할 수 있는지 잘 이해할수록,
        
    - “어떤 Agentic 워크플로를 만들 수 있을지” 상상하는 능력이 커진다.
        

### 7.6 Task Decomposition 요약

- 핵심 스킬:
    
    - “사람이 하는 복잡한 일”을 보고,
        
    - 이를 Agentic 워크플로로 구현 가능한 **작은 단계들로 쪼개는 능력**.
        
- 각 단계마다 스스로 묻는 질문:
    
    - “이 단계는 LLM 또는 API/함수/도구로 구현 가능한가?”
        
- 만약 “아직 어렵다”면:
    
    - “사람이라면 이 단계를 어떻게 할까?”
        
    - “그 과정을 더 작은 단계로 쪼개면,  
        그 중 일부는 LLM/툴로 구현 가능해지지 않을까?”
        
- 실제 개발에서는:
    
    - 처음 설계한 워크플로를 기반으로 구현 → 실행 결과 확인 →  
        부족한 부분을 찾아 **계속 분해·수정·개선**하는 반복이 매우 중요.

## 8. Eval(평가)과 Error Analysis 개요

### 8.1 왜 Eval이 중요한가

- 강의자의 경험:
    
    - 많은 팀과 Agentic 워크플로를 만들면서 본 바로는,
        
    - 누군가가 이 일을 **정말 잘하는지 여부를 가르는 핵심 요인** 중 하나:
        
        - **얼마나 체계적인 eval 프로세스를 운영하는가**.
            
- 이 영상의 목표:
    
    - Eval을 어떻게 만드는지 **간단한 개요**를 제공.
        
    - 이후 모듈에서 더 깊이 다룸.
        

### 8.2 평가를 언제/어떻게 만들까?

- 현실:
    
    - Agentic 워크플로를 만들고 나면,
        
    - **어떤 문제가 발생할지 사전에 전부 예측하기 매우 어렵다**.
        
- 권장 방식:
    
    1. 우선 워크플로를 구현하고,
        
    2. **실제 출력 결과를 많이 읽어보면서**,
        
    3. “이 부분이 마음에 안 든다”, “이런 행동은 문제다”라는 지점을 찾는다.
        
- 예: 경쟁사 언급 문제
    
    - 일부 비즈니스는 에이전트가 **경쟁사를 언급하는 것을 원하지 않음**.
        
    - 출력 예:
        
        - “우리와 함께 쇼핑해줘서 기쁩니다. 우리는 경쟁사 ComproCo보다 훨씬 낫습니다.”
            
        - “RivalCo와 달리 우리는 반환이 쉽습니다.”
            
    - 이런 문장은 기업 입장에서 **원하지 않는 행동**.
        
- 이 문제는:
    
    - 사전에 “이 에이전트가 경쟁사를 언급할 것이다”를 예측하기 어려운 사례.
        
    - 따라서:
        
        - **먼저 시스템을 만든 후**,  
            출력에서 문제를 발견한 뒤,
            
        - 이 문제를 줄이기 위한 **Eval과 개선**을 설계하는 것이 현실적.
            

### 8.3 객관적(Objective) Eval 예시: 경쟁사 언급

- 비즈니스가 경쟁사 언급을 오류로 간주한다면:
    
    - “경쟁사 언급 오류”를 줄이기 위한 eval을 추가할 수 있음.
        
- 방법:
    
    1. 경쟁사 목록(ComproCo, RivalCo, The Other Co 등)을 이름으로 정의.
        
    2. 에이전트의 출력 텍스트에서,
        
        - 이 이름들이 등장하는지 **코드로 탐지**.
            
    3. 전체 응답 중에서,
        
        - 경쟁사 언급이 발생한 비율을 계산.
            
- 장점:
    
    - 이 기준은 “mentioned / not mentioned”라는 **객관적 기준**.
        
    - 따라서 코드로 **자동 체크**하기 쉬움.
        

### 8.4 주관적(Subjective) Eval: LLM을 Judge로 사용

- 하지만 LLM의 출력이 **자유 텍스트**이다 보니,
    
    - 단순히 문자열 포함 여부로 측정하기 어려운 **주관적 품질 평가**도 필요.
        
- 예: 연구 에이전트의 에세이 품질 평가
    
    - 다른 LLM을 **평가자(judge)**로 사용:
        
        - “다음 에세이에 대해 1~5점의 품질 점수를 매겨라. 1은 최악, 5는 최고.”
            
    - 이때 `{{essay}}` 위치에 실제 에세이 텍스트를 삽입.
        
- 여러 주제에 대해 리포트 작성:
    
    - 예: 블랙홀 과학 최신 동향, 로봇을 이용한 과일 수확 등.
        
    - 평가 LLM이
        
        - 블랙홀 에세이에 3점,
            
        - 로봇 수확 에세이에 4점 등 점수를 줄 수 있음.
            
    - 워크플로를 개선할수록 이 점수가 올라가야 함.
        
- 한계:
    
    - LLM은 1~5점 같은 **단순 스케일 점수에 대해 아주 뛰어난 일관성을 보여주지 못함**.
        
    - 강의자는 개인적으로 이 방식(1~5 점수)은 많이 쓰지 않는다고 언급.
        
    - 이후 모듈에서 더 **정교한 LLM-as-judge 기법**을 다룰 예정.
        

### 8.5 Eval의 종류: End-to-End vs Component-level

- 이 코스에서 다루는 두 가지 큰 Eval 유형:
    
    1. **End-to-End Eval**:
        
        - 에이전트 전체를 하나의 시스템으로 보고,
            
        - 최종 출력의 품질을 평가.
            
    2. **Component-level Eval**:
        
        - Agentic 워크플로 안의 **단일 단계**에 대해 별도로 평가.
            
        - 예: “검색어 생성 품질”, “정보 추출 정확도” 등.
            
- 용도:
    
    - End-to-end와 component-level Eval은
        
        - 개발 과정에서 **서로 다른 종류의 개선 작업**에 도움을 줌.
            

### 8.6 Error Analysis: 중간 출력(Trace) 읽기

- 또 하나의 핵심 도구:
    
    - **에이전트의 중간 출력(trace)을 직접 읽어보는 것**.
        
- Error Analysis란:
    
    - 워크플로의 각 단계에서 LLM이 어떤 중간 결과를 만들었는지 모두 들여다보며,
        
    - 어디서 기대와 다르게 동작하는지,
        
    - 어떤 부분을 개선해야 할지 찾는 과정.
        
- 요약:
    
    - Eval 설계 + Error analysis 능력은
        
        - Agentic 워크플로를 잘 만드는 데 **매우 중요한 스킬**.
            
    - 이 주제는 4번째 모듈에서 더 깊게 다룸.

## 9. 핵심 Design Pattern 개요 (Reflection, Tool Use, Planning, Multi-Agent)

### 9.1 네 가지 주요 디자인 패턴

- Agentic 워크플로는 빌딩 블록들을 조합해 만든다.
    
- 이 조합 방식에서 반복적으로 등장하는 핵심 패턴 네 가지:
    
    1. **Reflection**
        
    2. **Tool Use**
        
    3. **Planning**
        
    4. **Multi-Agent Collaboration**
        
- 이 영상에서는 개념을 짧게 소개하고,
    
    - 이후 모듈에서 각각을 깊게 다룰 예정.
        

### 9.2 Reflection 패턴

- 기본 아이디어:
    
    - LLM에게 어떤 출력(예: 코드)을 생성하게 하고,
        
    - 다시 그 LLM(또는 다른 LLM)에게 그 출력을 **비판/리뷰**하게 한 뒤,
        
    - 피드백을 반영하여 더 나은 출력을 다시 생성.
        
- 코드 예:
    
    1. LLM이 Python 함수 코드를 생성.
        
    2. 다음과 같은 프롬프트 구성:
        
        - “다음 코드는 특정 태스크를 위해 작성된 코드다.  
            correctness, style, efficiency 측면에서 조심히 검토하고  
            건설적인 피드백을 제공하라.”
            
        - 여기에 1단계에서 생성한 코드를 붙인다.
            
    3. LLM이 코드의 문제점, 비효율, 스타일 이슈 등을 지적.
        
    4. 그 피드백을 다시 프롬프트에 넣고:
        
        - “위 피드백을 반영해 코드를 고쳐라.”
            
    5. LLM이 개선된 v2 코드를 생성.
        
- Tool use와 결합:
    
    - 코드를 실행하고, 에러 메시지를 LLM에 다시 전달하면,
        
    - 그 정보를 이용해 v3 코드로 재수정할 수 있음.
        
- 요약:
    
    - Reflection은 **자기 출력을 다시 보고 고치는 반복 구조**.
        
    - 마법처럼 모든 걸 해결해 주는 것은 아니지만,
        
    - 시스템 성능에 **꽤 의미 있는 향상**을 주는 경우가 많음.
        
- Multi-agent 관점 미리보기:
    
    - 한 LLM이 스스로를 비판할 수도 있지만,
        
    - “Critique Agent”라는 별도 역할을 만든다고 생각할 수도 있음.
        
        - 역할: “코드를 비판/리뷰하는 에이전트”
            
        - 이 에이전트가 코드를 읽고 피드백.
            
    - 또 다른 에이전트가 이 피드백을 받아 코드를 수정.
        
    - 이렇게 **서로 다른 역할의 에이전트 간 상호작용**으로 볼 수도 있음.
        

### 9.3 Tool Use 패턴

- 개념:
    
    - LLM에게 “툴을 사용할 수 있는 능력”을 제공.
        
    - 툴 = LLM이 호출할 수 있는 함수들.
        
- 예:
    
    - “리뷰 기준 최고의 커피머신이 무엇인지 알려줘”:
        
        - LLM이 웹 검색 툴을 호출해 실제 정보를 찾아보고 답함.
            
    - “100달러를 복리로 투자했을 때 n년 뒤 금액은?”:
        
        - LLM이 코드 실행 툴을 사용해 계산 코드 작성 → 실행 → 정확한 결과.
            
- 오늘날 존재하는 다양한 툴:
    
    - 수학, 데이터 분석.
        
    - 정보 수집(웹, DB).
        
    - 이메일·캘린더 같은 생산성 앱 제어.
        
    - 이미지 처리 등.
        
- 포인트:
    
    - LLM이 **어떤 툴을 언제 사용할지 결정**할 수 있을 때,
        
    - 단순 텍스트 생성만 할 때보다 훨씬 광범위한 작업을 수행 가능.
        

### 9.4 Planning 패턴

- 예: HuggingGPT 논문에서의 예시
    
    - 입력:
        
        - “소년의 포즈와 같은 자세로 책을 읽는 소녀 이미지 생성,  
            그리고 그 이미지를 너의 목소리로 묘사해 달라.”
            
    - LLM의 계획:
        
        1. 포즈 추출 모델 호출: 소년 이미지에서 포즈 추출.
            
        2. 이미지 생성 모델 호출: 추출한 포즈를 이용해 소녀 이미지 생성.
            
        3. 이미지 캡셔닝/텍스트 생성: 생성된 이미지를 설명하는 문장 생성.
            
        4. TTS(text-to-speech) 호출: 설명 문장을 음성으로 변환.
            
- Planning이란:
    
    - 개발자가 모든 API 호출 순서를 미리 하드코딩하는 대신,
        
    - LLM이 **필요한 작업 순서를 스스로 설계**하고,
        
    - 그 순서에 따라 실제 툴 호출을 실행하는 것.
        
- 특징:
    
    - 계획을 세우는 에이전트는 **통제하기가 더 어렵고**,
        
    - 예상치 못한 행동을 할 수 있으며,
        
    - 아직 **실험적 성격**이 강함.
        
    - 하지만 성공할 경우 **매우 흥미롭고 강력한 결과**를 만들어 내기도 함.
        

### 9.5 Multi-Agent Collaboration 패턴

- 사람 조직 비유:
    
    - 복잡한 프로젝트를 수행할 때,
        
        - 매니저가 여러 사람(연구자, 디자이너, 엔지니어, 에디터 등)을 고용해 협업하게 함.
            
    - 마찬가지로, 복잡한 태스크를 위해 **서로 다른 역할의 여러 에이전트**를 협업시키는 구조.
        
- 예: ChatDev 프로젝트
    
    - Chen Qian 등 연구자들이 만든 소프트웨어 프레임워크.
        
    - CEO, Programmer, Tester, Designer 등 **각기 다른 역할의 에이전트**들이
        
    - 가상의 소프트웨어 회사처럼 협력해 다양한 개발 작업 수행.
        
- 또 다른 예: 마케팅 브로슈어 작성
    
    - 사람 팀:
        
        1. 연구자: 온라인 리서치.
            
        2. 마케터: 마케팅 텍스트 작성.
            
        3. 에디터: 텍스트 편집 및 다듬기.
            
    - Multi-agent 워크플로:
        
        - research agent, marketer agent, editor agent를 각각 시뮬레이션하여
            
        - 이 세 에이전트가 협업하게 할 수 있음.
            
- 특징:
    
    - Multi-agent 시스템은 **통제가 더 어렵고**,
        
    - 에이전트들이 무엇을 할지 완전히 예측하기 힘듦.
        
    - 하지만 연구 결과에 따르면,
        
        - 일부 복잡한 태스크(전기, 바이오그래피, 체스 수 등)에서
            
        - **단일 에이전트보다 더 나은 결과**를 내기도 함.
            

### 9.6 정리 및 다음 모듈 예고

- 지금까지:
    
    - Agentic 워크플로가 무엇인지,
        
    - 어떤 애플리케이션에서 쓰이고,
        
    - Task decomposition, Eval, 주요 디자인 패턴 등을 개괄적으로 확인.
        
- 이 코스의 핵심 과제:
    
    - 적절한 빌딩 블록들을 찾고,
        
    - Reflection, Tool Use, Planning, Multi-agent 같은 패턴을 이용해 조합하고,
        
    - Eval로 성능을 측정·개선하는 것.
        
- 다음 모듈:
    
    - 네 가지 디자인 패턴 중 첫 번째인 **Reflection**을 깊게 파고들 예정.
        
    - 구현은 생각보다 단순하지만,
        
    - 시스템 성능을 **꽤 크게 끌어올릴 수 있는 테크닉**임.
